# PA2-3 阶段总结：加入 IOE 并打通 AM 设备访问链路

## 本阶段目标

本阶段的目标是根据 `periodical-summary/instruction.md`，在 NEMU 与 `nexus-am` 的 `x86-nemu` 平台之间补齐 IOE 相关功能，让 AM 程序可以通过统一 API 访问：

- 串口
- 时钟 RTC
- 键盘
- VGA 显存

最终效果是让 `hello`、`timetest`、`keytest`、`videotest` 这类 AM 程序可以在 NEMU 上运行，并通过端口 I/O 或 MMIO 与设备完成交互。

## 主要实现内容

### 1. 打开 NEMU 的 IOE 总开关

修改文件：

- `nemu/include/common.h`

关键点：

- 定义 `HAS_IOE` 宏，触发 `init_device()` 初始化串口、时钟、键盘、VGA。
- 这样 NEMU 启动后，设备模型会被真正注册到 PIO/MMIO 空间中，而不是仅保留框架代码。

### 2. 实现 `in/out` 指令，打通 AM 到端口设备的访问

修改文件：

- `nemu/src/cpu/exec/system.c`
- `nemu/src/cpu/exec/exec.c`
- `nemu/src/cpu/exec/all-instr.h`
- `nemu/include/cpu/exec.h`

关键点：

- 在 `exec_in()` 中调用 `pio_read()`，把读取到的数据写回目的操作数。
- 在 `exec_out()` 中调用 `pio_write()`，把源操作数写到目标端口。
- 为 `0xe4/0xe5/0xe6/0xe7` 和 `0xec/0xed/0xee/0xef` 补上 opcode 表项。
- 由于 NEMU 的设备行为和 QEMU 不完全一致，继续保留 `diff_test_skip_qemu()`，避免差分测试误报。

联动关系：

- `AM _putc()` 通过串口 `0x3f8` 输出字符。
- `_uptime()` 通过 `RTC_PORT 0x48` 读取毫秒时间。
- `_read_key()` 通过 `0x64/0x60` 查询键盘状态和数据。

### 3. 在物理内存访问中加入 MMIO 判断

修改文件：

- `nemu/src/memory/memory.c`

关键点：

- 在 `paddr_read()` / `paddr_write()` 中先调用 `is_mmio()` 判断地址是否落入 MMIO 映射。
- 若命中 MMIO，则改为调用 `mmio_read()` / `mmio_write()`。
- 若未命中，则继续访问 `pmem`。

联动关系：

- VGA 的 framebuffer 映射在 `0x40000`。
- AM 侧 `_draw_rect()` 直接向 `fb` 指针写像素时，最终会走到 NEMU 的 MMIO 路径，而不是普通内存。

### 4. 实现 `x86-nemu` 平台的 IOE API

修改文件：

- `nexus-am/am/arch/x86-nemu/src/ioe.c`
- `nexus-am/am/arch/x86-nemu/src/trm.c`

实现内容：

- `_ioe_init()`：记录启动时 RTC 时间，作为 `_uptime()` 基准。
- `_uptime()`：返回 `inl(RTC_PORT) - boot_time`。
- `_read_key()`：先读状态端口 `0x64`，有按键再从 `0x60` 读取 AM 键值。
- `_draw_rect()`：按行把 `pixels` 拷贝到 `0x40000` framebuffer，对越界区域进行裁剪。
- `_draw_sync()`：在 NEMU 下保持空实现，因为显存写入后会由设备刷新逻辑同步到窗口。
- 在 `trm.c` 中打开 `HAS_SERIAL`，让 `hello` 等程序能真正通过串口输出。

### 5. 补齐 `klib`，打通 AM 应用的构建链路

修改文件：

- `nexus-am/libs/klib/Makefile`
- `nexus-am/libs/klib/src/klib.c`

关键点：

- 为 `klib` 增加正式的 `Makefile`，让 `make -C nexus-am/apps/...` 时能够自动构建 `klib-x86-nemu.a`。
- 实现一套最小但可用的运行库函数，覆盖本阶段应用和测试需要的能力：
  - 内存与字符串：`memset`、`memcpy`、`memmove`、`memcmp`、`strlen`、`strcmp`、`strcpy` 等
  - 基础运行时：`kalloc`、`atoi`、`abs`、`rand`、`srand`
  - 输出：`printf`、`sprintf`、`snprintf`、`vsprintf`、`vsnprintf`
- 这样 `typing`、`hello`、`timetest`、`keytest`、`videotest`、`litenes` 在链接时都能拿到需要的符号，而不是在 `rand`、`printf`、`strlen` 处失败。

联动关系：

- `typing` 依赖 `rand()` 生成字母、依赖 `strlen()` 计算 HUD 文本宽度。
- `litenes` 和多个测试程序依赖 `printf()`、`memset()`、`memcmp()` 等基本库函数。

### 6. 为跑通 AM 程序补齐必要的前置指令支持

修改文件：

- `nemu/src/cpu/exec/exec.c`
- `nemu/src/cpu/exec/arith.c`
- `nemu/src/cpu/exec/logic.c`
- `nemu/src/cpu/exec/control.c`
- `nemu/src/cpu/exec/data-mov.c`
- `nemu/src/cpu/exec/cc.c`
- `nemu/src/cpu/exec/all-instr.h`

原因：

- 当前 `pa2` 基线中，仍有一批 PA2 阶段常用指令没有真正接入 opcode 表或仍为 `TODO()`。
- 虽然这些并不属于 IOE 设备本身，但 AM 程序在进入 `main()`、执行循环、调用 `printf()` 或进行图形计算时会立即触发它们。

这次补齐的关键前置能力包括：

- `push r/m32`、`call_rm`、`jmp/jcc`
- `inc/dec`
- `test/or`
- `not/neg`
- `shl/shr/sar`
- `mul/imul/div/idiv`
- `movsx/movzx`
- `cwtl/cltd`
- `nop`
- `rtl_setcc()`
- `sub imm -> eax`
- `gp4` 组中的 8 位 `inc/dec`

这些修改的作用是保证 AM 程序和小游戏可以顺利跑到 IOE 相关代码，而不是提前死在基础指令缺失上。

## IOE 链路理解

本次实现中，设备访问的完整链路如下：

1. AM 程序调用 `_putc()`、`_uptime()`、`_read_key()` 或 `_draw_rect()`
2. `x86-nemu` 平台代码分别发起 `in/out` 指令或直接写 framebuffer 地址
3. CPU 在 NEMU 中执行这些指令
4. 若是端口 I/O，则进入 `pio_read()` / `pio_write()`
5. 若是显存写入，则在 `paddr_*()` 中识别为 MMIO，进入 `mmio_write()`
6. 设备模型更新状态
7. NEMU 定时调用 `device_update()`，处理键盘事件、刷新 VGA 窗口

最关键的联动点有两个：

- `in/out` 是串口、RTC、键盘三种设备的入口
- `paddr_*()` 中的 MMIO 分流是 VGA 生效的前提

## 遇到的问题与解决方法

### 问题 1：当前环境缺少 32 位开发头文件，`nexus-am` 无法直接 `-m32` 编译

现象：

- 编译 `hello` 时，`stdint.h` 继续包含 `gnu/stubs-32.h` 失败。

解决：

- 没有直接安装系统包，而是下载 32 位相关 `.deb` 到本地，解包成临时 sysroot。
- 通过 `C_INCLUDE_PATH` / `CPLUS_INCLUDE_PATH` / `LIBRARY_PATH` 让 `gcc -m32` 能正常找到头文件和库。

### 问题 2：仓库中缺少可构建的 `klib`

现象：

- `make -C nexus-am/apps/...` 时，`klib` 构建步骤失败。
- `typing` 在链接阶段报 `undefined reference to rand`。
- 其它 AM 程序也可能在 `printf`、`strlen`、`memset` 等常见符号处失败。

解决：

- 直接在仓库中补上 `nexus-am/libs/klib/Makefile` 和 `src/klib.c`。
- 让 `klib` 作为正式库参与构建，而不是依赖临时产物或手工链接。

### 问题 3：`hello`/`timetest`/`typing`/`litenes`/`videotest` 首次运行不断撞到 `invalid opcode`

现象：

- 先后在 `push r/m32`、`nop`、`gp3 div`、`gp2 shift`、`or`、`imul`、`sub imm -> eax`、`gp4 dec r/m8` 等位置中断。

原因：

- `pa2` 当前基线里，很多执行 helper 已存在，但 opcode 表未接线；也有一部分 helper 仍是 `TODO()`。

解决：

- 采用“运行 AM 程序 -> 定位首个缺失指令 -> 补齐接线/实现 -> 回归”的方式逐步补齐。
- 先保证 `hello` 跑通，再扩展到 `timetest`、`typing`、`litenes`、`videotest` 会覆盖到的公共路径。

### 问题 4：`typing` 显示 0 FPS，键盘看起来没有反应

现象：

- `typing` 可以启动，但界面长期显示 `0 FPS`。
- 按键事件几乎不生效，看起来像键盘输入失灵。

原因：

- `nemu/include/common.h` 中默认打开了 `DEBUG`。
- 在该模式下，NEMU 会持续记录大量指令日志，导致执行速度大幅下降。
- PA2-3 的设备计时器使用虚拟定时器，NEMU 被日志输出拖慢后，`_uptime()` 增长、屏幕刷新和键盘轮询都会明显失真，因此小游戏表现为“低 FPS / 无响应”。

解决：

- 将 `DEBUG` 默认关闭，把当前仓库的默认运行模式切回更接近正常执行速度的状态。
- 需要调试指令执行时，再手动重新打开 `DEBUG` 宏。

### 问题 5：`litenes` 运行时在 `0x80 /1` 形式的 `or` 指令处报 `invalid opcode`

现象：

- 输入 `c` 后在 `invalid opcode(eip = 0x001068c4): 80 cd 3f ...` 中断。

原因：

- `0x80/0x81/0x83` 共用的 `gp1` 组表里，只接入了 `add/adc/and/sub/xor/cmp`。
- 其中 `/1` 对应的 `or` 没有注册，因此遇到 `or imm8, r/m8` 会直接掉进 `inv`。

解决：

- 在 `gp1` 组表中把 `/1` 补为 `EX(or)`，让 `0x80 /1`、`0x81 /1`、`0x83 /1` 都能走到 `exec_or()`。

## 验证情况

已经完成的验证：

- `hello-x86-nemu.bin`：成功打印 10 行 `Hello World!`，并触发 `HIT GOOD TRAP`
- `timetest-x86-nemu.bin`：成功连续输出 `1 second.`、`2 seconds.`、`3 seconds.`、`4 seconds.`
- `keytest-x86-nemu.bin`：成功编译并启动，在无头 SDL 环境下可稳定进入事件循环，无 `invalid opcode`
- `videotest-x86-nemu.bin`：成功编译并启动，在无头 SDL 环境下可稳定进入主循环，无 `invalid opcode`
- `typing-x86-nemu.bin`：成功编译、链接并进入游戏循环，无 `invalid opcode`
- `litenes-x86-nemu.bin`：成功编译、链接并进入游戏循环，无 `invalid opcode`
- 关闭 `DEBUG` 后，`typing` 的 FPS 与键盘响应恢复正常
- 补齐 `gp1 /1 -> or` 后，`litenes` 不再在 `80 cd 3f` 处报 `invalid opcode`

说明：

- 由于当前环境没有可用的图形桌面/输入注入工具，`keytest` 的按键输出、`videotest` 的动画画面，以及 `typing/litenes` 的可视交互部分未做自动化截图验收。
- 但从编译、链接、启动、指令执行、IOE 接口打通和主循环稳定性来看，PA2-3 的主功能链路已经接好。
